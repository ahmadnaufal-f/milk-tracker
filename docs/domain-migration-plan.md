# Milk Tracker: domain migration notice implementation plan

Prepared and updated on 2026-10-05 from `ahmadnaufal-f/milk-tracker`, default branch `main`, commit `c79287ac174d5922a6fb9c5413873d7595704d28`. Includes the requested guest migration without Google login and mandatory unit/integration testing. Application changes are implemented on `codex/domain-migration`; hosting has not been deployed. Paths marked **new** identify additions. See [domain-migration-rollout.md](domain-migration-rollout.md) for configuration and release checks.

Goal: notify people opening the old PWA, guide them to the new domain, and help them reinstall without losing accessible records. The destination is `https://pump.arkaes.dev`, confirmed ready by the owner on October 5, 2026; HTTPS availability has been verified. The old domain expires on November 10, 2026; use the date-only value `2026-11-10` and tell users to move before that date. The confirmed old production origin is `https://pump.a-naufal.dev`. Prepare the implementation now; keep migration disabled until the migration deployment has been verified. The old-origin allowlist defaults to the confirmed old domain.

Baseline repository findings: React/Vite uses `vite-plugin-pwa` with `registerType: 'autoUpdate'`; the manifest launches `./index.html`. Firebase Auth supports Google and anonymous guests. Firestore records and settings live under `users/{uid}`, with persistent browser caching. Pumping state uses localStorage keys `pumping_startTime` and `unsavedSession`. `AppBanner` currently prioritizes guest and privacy notices and only mounts in `MainLayout`, excluding login and settings. Notification setup registers `/firebase-messaging-sw.js` at `/`, overlapping the generated PWA worker. Notification clicks currently open the worker's own origin.

An installed PWA cannot generally be moved to another origin by changing its manifest or redirecting it. Users need to open and install the new site. Auth sessions, browser storage, notification permissions, and push subscriptions do not transfer automatically. Synced Firestore data can remain available when the new site uses the same Firebase project and the same user UID.

## 1. Add explicit migration configuration and PWA detection

**Files:** `src/config/domainMigration.ts` (**new**), `src/lib/pwa.ts` (**new**), `src/vite-env.d.ts`, `src/main.tsx`.

Define `DomainMigrationConfig` with a campaign ID, enabled flag, old-origin allowlist, nullable destination origin, and nullable retirement date. Add `getDomainMigrationConfig()` and `isOldMigrationOrigin()`. Default to disabled. Require a valid HTTPS destination distinct from the old origin before exposing a navigation action; never create a link to a placeholder. Gate on exact old origins so the notice does not appear on the destination, preview deployments, or Firebase fallback domains unless explicitly configured.

Implement `isStandalonePwa()` using display-mode detection and iOS `navigator.standalone`, and reuse it in `src/main.tsx`. Provide detailed reinstall guidance for standalone launches. Also show a concise notice in old-domain browser visits: browsers do not offer reliable detection of every previously installed PWA.

A separate announcement state may say that the app will move while the destination is pending, without a migration button. The enabled flag permits rollback; configuration changes require another build/deployment, and already cached offline clients cannot receive them immediately.

## 2. Show a prominent notice with a reusable migration guide

**Files:** `src/components/DomainMigrationNotice.tsx` (**new**), `src/pages/DomainMigrationPage.tsx` (**new**), `src/components/Banner.tsx`, `src/App.tsx`, `src/pages/SettingsPage.tsx`, `src/data/tutorial-en.md`, `src/data/tutorial-id.md`.

Create `DomainMigrationNotice` and `DomainMigrationPage`; add a public `/migration` route accessible before sign-in. Mount `AppBanner` once inside `App`'s `PumpingProvider`, outside the individual route layouts. Extend `ActiveBanner` with migration priority and retain the existing route eligibility of guest/privacy notices. Migration eligibility must not depend on authentication completing.

Show a compact migration banner whenever the campaign applies. On the first eligible standalone launch, show an accessible dialog explaining the move; “Remind me later” snoozes the dialog for 24 hours using a campaign-specific timestamp, while the compact banner and Settings guide remain available. Opening the destination must not count as confirmed migration or permanently suppress the notice. Dialog dismissal must not interrupt pumping or saving.

The guide contains the actual destination, the retirement date when known, and the appropriate action: “Move my guest data” for guests or “Open new app” for Google users. Everyone finishes and syncs records first. Guests use the one-time transfer in step 3 without Google login; Google users sign in on the destination with the same account. Then verify history/settings, install the new app, enable reminders there when supported, and finally remove the old home-screen app. Android instructions use the browser's install option, with a native install prompt where supported. iOS instructions use Safari's Share → Add to Home Screen. Provide a copy-address option if the old standalone window makes opening the browser difficult; guest transfer links must be clearly identified as private, short-lived links. Preserve the repository's existing English/Indonesian tutorial pattern.

Suggested copy: “Milk Tracker is moving to a new web address. To keep using the installed app, open the new site and add it to your home screen again. Finish and sync your current session first.” Display a deadline only when supplied.

Copy and interaction requirement: use gentle, reassuring, respectful language for mothers who may be tired or caring for a baby. Keep each instruction short, give one clear next step, and let users pause and continue later. Avoid alarming headlines, blame, guilt, artificial urgency, patronizing terms, and technical jargon. Be accurate about data safety: say records are ready only after server confirmation; never promise that unverified changes are safe. Prefer “We're moving to a new home,” “Let's save your latest session first,” “Move my records,” “I'll do this later,” and “Your records are ready. You can add the new app to your home screen when you're ready.” For retry states, explain what happened calmly and state that records have not been removed when verified. Include copy review and accessibility checks in acceptance testing. Use the requested Impeccable skill for the notice, guide, progress, and recovery states while retaining the app's existing visual style.

## 3. Transfer guest access without Google login and preserve all records

**Files:** `src/hooks/usePumpingControl.tsx` (`PumpingProvider`), `src/services/storage.ts`, `src/services/guestMigration.ts` (**new**), `src/services/accountLinking.ts` (**new**), `src/contexts/AuthContext.tsx` (`AuthProvider`, `useAuth`), `src/components/Banner.tsx` (`GuestBanner.handleLink`), `src/pages/SettingsPage.tsx` (`handleLinkAccount`), `src/pages/LoginPage.tsx`, `src/pages/DomainMigrationPage.tsx`, `src/components/DomainMigrationNotice.tsx`, `functions/src/guest-migration.ts` (**new**), `functions/src/index.ts`, `functions/src/cleanup-anonymous-users.ts` (`cleanupAnonymousUsers`), `firestore.rules`.

Add `prepareForDomainMigration()` in the storage service to wait for pending Firestore writes using `waitForPendingWrites(db)` and confirm connectivity to Firestore. Use a bounded UI wait with retry/cancel; `navigator.onLine` alone does not prove synchronization. A successful migration check must also require no running timer, no save in progress, and no `unsavedSession` or `pumping_startTime`. Keep the destination action unavailable until these checks succeed, and recheck immediately before navigation. Do not clear local storage, sign users out, or silently discard a session.

For Google users, explain that signing in again with the same account restores synced records and settings. For guests, transfer access to the existing Firebase UID using a short-lived, single-use handoff. Guest records are already in Firestore; do not create a temporary copy of their history or delete the original records. Saving and synchronizing the local draft before transfer is required in the first version. Carrying a running timer or unsaved draft to the destination is outside this version's scope.

Implement authenticated `createGuestMigration`, code redemption via `redeemGuestMigration`, and authenticated `confirmGuestMigration` Cloud Functions, exported in `functions/src/index.ts`. Separate their core logic from the callable wrappers so unit tests can inject the database, token signer, and clock. The backend owns the allowed destination and campaign configuration; it must not trust a client-supplied UID or arbitrary destination URL.

`createGuestMigration` verifies the caller's guest identity, migration eligibility, and destination readiness after the client passes the sync/session checks. Generate at least 256 bits of randomness and return a private destination link such as `/migration#transfer=...`. Store only the code digest in a private top-level `guestMigrations` collection with the source UID, campaign/destination, server expiry (approximately 10 minutes), and transfer status. Explicitly deny client reads/writes in `firestore.rules`; all access goes through trusted backend code. Enforce server expiry even before Firestore TTL deletion runs, enforce App Check where supported, and rate-limit issuance/redemption. Never log the code, link fragment, or Firebase custom token.

`DomainMigrationPage` reads the fragment into memory, removes it from the address bar before unrelated navigation, and redeems it over HTTPS. `redeemGuestMigration` checks the digest, campaign, configured destination, server expiry, and status, and uses an atomic Firestore transaction to allow one successful claim even with simultaneous requests. Mint a Firebase custom token only for the source UID in the stored grant. Return it over HTTPS, never in a URL or localStorage. `completeGuestMigration()` in the client service calls `signInWithCustomToken()` for that UID; it must not create a fresh anonymous account and leave the old data behind. If the destination already has a different signed-in identity, handle the account switch explicitly rather than silently replacing it or merging data.

Treat redemption and completion as separate states. Show “Migration complete” only after the destination has authenticated as the expected UID, fetched history/settings from the server using that client's Firebase credentials, and successfully called `confirmGuestMigration`. Cached reads, opening the link, or issuing a custom token do not count as successful migration. Confirmation checks the authenticated UID against the stored grant and is idempotent, so retrying confirmation cannot duplicate records or reminders. Remove the transfer secret from client memory after use. A consumed or expired code requires a fresh link from the still-usable old app; failed sign-in or a lost response must never delete its data. Server reads also distinguish an empty history from a failed history fetch.

Keep all user records, settings, and applicable subcollections under the original `users/{uid}` path. Only transfer grants expire; Firestore TTL is configured on the grant expiry field, not user data. The old origin's local data remains until completion is verified; no cross-origin clearing is possible. In the first version, retain it until the user removes the old installation rather than automatically clearing it. Do not sign out or revoke the source guest session during the transfer.

Custom-token sign-in may change Firebase's `user.isAnonymous` behavior. Introduce explicit app-level guest status based on verified identity/profile metadata in `AuthProvider`, and update `useAuth` consumers so transferred guests remain guests and linking stays optional. `cleanupAnonymousUsers` already uses the Firestore `isAnonymous` and `lastActive` fields; refresh `lastActive` at issuance, completion, and subsequent guest activity, and exclude in-progress transfers until their grants expire. Recheck eligibility before deletion to avoid deleting a user who has just migrated or become active. Preserve the existing guest retention policy and test its behavior for transferred guests.

Optional Google linking remains available. Move its logic into `linkGuestAccount()` for consistent handling. Both existing handlers automatically switch accounts on `auth/credential-already-in-use`; that does not merge guest records. Keep the guest identity intact on this error and offer the guest transfer route or another Google account. Automatic account merging is outside this implementation.

## 4. Make the notice reachable through service-worker updates

**Files:** `vite.config.ts`, `src/main.tsx`, `src/services/notifications.ts` (`getFCMToken`), `public/firebase-messaging-sw.js`, `public/firebase-messaging-handler.js` (**new**), `firebase.json`.

Use one worker implementation for both Workbox caching and FCM. Keep the generated `/sw.js` worker, move the FCM handlers into an imported script via Workbox `importScripts`, and make `getFCMToken()` use that worker's activated registration. Retain the legacy `/firebase-messaging-sw.js` URL as a compatibility worker importing `/sw.js` during the transition, so older cached bundles that register it continue to use equivalent behavior. Avoid circular imports and keep the scope `/`.

Change update handling to a controlled refresh (`registerType: 'prompt'` with explicit registration). Check for updates on launch and on return to the foreground, with throttling. When a new worker is ready, show an update action and activate/reload only after saving the current session and confirming synchronization. The first upgrade must still tolerate the already-shipped auto-update behavior; only future releases can use the new guard. Verify the bundled registration is not duplicated.

Keep HTML and worker scripts revalidated through Firebase Hosting, retain immutable caching for hashed assets, and ensure `/migration` works after a direct navigation. Bundle the notice and guide in the precache so they remain available offline after a successful update. An offline user still cannot navigate to the new domain until connectivity returns.

The notice must be deployed on the old origin while DNS and HTTPS still work. Users on older cached builds need an online launch/update to receive it. No implementation can guarantee delivery to inactive installations once control of the old domain is lost. Preserve a migration overlap, extending the old registration if needed; a redirect cannot operate after DNS/HTTPS access is gone. Avoid a blanket redirect while guests and unsynced records still need the old app.

## 5. Validate the destination, migration flow, and rollout

**Files/configuration:** `src/firebase.ts`, `src/components/BasePage.tsx`, `src/services/notifications.ts`, `functions/src/send-notifications.ts` (`sendDueNotifications`, `APP_URL`), `vite.config.ts`, `firebase.json`, `package.json`, `functions/package.json`, `vitest.config.ts` and `functions/vitest.config.ts` (**new**), Firebase Auth and reCAPTCHA/App Check domain settings, Firestore TTL settings for transfer grants, `docs/domain-migration-plan.md` (**new**, repository copy of this plan).

Prepare configuration/UI, guest-transfer backend/client, data checks, tests, and worker consolidation as independently reviewable changes. Tests are required deliverables alongside the implementation. Once the destination is supplied, configure HTTPS and Hosting, retain the existing Firebase project, authorize the new domain for Google sign-in, and allow it in the reCAPTCHA/App Check configuration. Verify guest transfer, Google sign-in, and Firestore access before enabling the destination action on the old site. Test manifest installation at the new origin without trying to change the installed old app's identity.

On the destination, request notification permission through an explicit user action and obtain/save a new origin-specific FCM token. Validate both foreground and background reminders. The current data model stores only one `fcmToken` per user; enabling the new installation replaces that token, so do not promise simultaneous reminders on both installations. Keep migration campaign notifications out of this implementation unless separately requested. Verify the interaction between the backend `APP_URL` and worker click handler before changing reminder links; old and new registrations must route to a working app during overlap.

The reminder functions are currently commented out in `functions/src/index.ts`; preserve their current enablement. Implementing guest migration must not inadvertently turn reminder sending on.
